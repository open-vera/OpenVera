# OpenVera v0.3.0 Release Notes

OpenVera v0.3.0 focuses on smoother migration, better CLI usability, more reliable model switching, faster local development, and the **Vera Control Gateway** control plane (available in the monorepo workspace).

## Highlights

### Claude Code Configuration Migration

OpenVera can now migrate existing Claude Code configuration, making it easier to bring over provider, model, and API key settings without re-entering everything manually.

### New `vera sync` Command

A new `vera sync` command is available for syncing external agent resources and keeping local OpenVera resources (`.vera/`, skills, etc.) aligned.

### CLI Aliases

The CLI now supports additional command aliases:

```bash
vera
ai
```

You can continue using `openvera` as before.

### Improved First-Run Setup

The first-run setup experience has been improved. If no API key is configured, OpenVera will guide users through an interactive setup flow.

### Vera Control Gateway (Workspace)

This release adds a unified **Gateway control plane** in the monorepo: discovery, capability inventory, run observability, and management actions—while execution stays in Core / Harness.

- New package: `@open-vera/gateway` (project registry, capability descriptors, Doctor checks)
- New app: `apps/gateway-ui` (Vue web + Node HTTP server)
- REST API: `/api/gateway/*`, `/api/projects`, `/api/runs`, `/api/conversations`, etc. (no legacy `/api/admin` compatibility layer)
- UI areas: Projects, Capabilities, Runs (flow launcher + nested run views), Chat, RAG, MCP, Operations, Cost, Doctor

Local startup:

```bash
pnpm gateway-serve          # API server (default :7720)
pnpm ui                     # Web UI
pnpm gateway-serve:dist     # API from compiled dist
```

> Gateway UI ships with the repository and is not yet published as a standalone npm package; the `openvera` CLI install does not include the web UI.

## Provider And Model Switching

Provider and model switching in the REPL is more reliable. OpenVera now preserves the default provider model fallback behavior, reducing cases where switching models could accidentally lose or override the expected fallback.

## Development Workflow

### Harness dev loads Core source directly

Harness / `openvera` dev mode resolves `@open-vera/core` TypeScript sources under `--conditions=development`. After editing `packages/core/src`, test with:

```bash
pnpm dev
# or
pnpm repl
```

without rebuilding core first.

### REPL startup fix

Fixed `React is not defined` when `tsx` did not apply `react-jsx` across workspace packages: React import in `App.tsx` and explicit `--tsconfig` on dev scripts.

## Installation

```bash
npm install -g @open-vera/openvera@0.3.0
```

Or run with:

```bash
npx @open-vera/openvera@0.3.0
```

Gateway from source:

```bash
git clone <repo>
cd open-vera && pnpm install
pnpm gateway-serve
pnpm ui
```

## Notes

- The `0.3.0` npm publish is currently blocked by npm authentication or permission issues. If the package is not available yet, it will be published once registry access is restored.
- Flows and iteration artifacts live under `.vera/flows/` (including `iterations/`). Migrate away from legacy `.flow/` paths if needed.
- Gateway chat and RAG vector search: basic APIs and Core `runAgent` integration are in place; full MCP tool invocation and embedding-based RAG search are follow-up work.
