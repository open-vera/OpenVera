# OpenTUI 切换方案

> Vera 当前 TUI 基于 React + Ink 构建（详见 [tui.md](./tui.md) 和 [tui-ink.md](./tui-ink.md)）。本文评估用 OpenTUI 重写终端界面的可行性与代价，为后续技术选型提供决策依据。

## 背景

Vera TUI 经过多次迭代已具备完整功能——对话面板、Diff 查看器、Slash 命令系统、Plan Mode 可视化等（17 个命令、5 种 Overlay、22 个组件约 3000+ 行 TSX）。在此基础上，任何重写方案都必须回答三个核心问题：

1. **功能等价**：能否覆盖现有全部能力？
2. **迁移代价**：重写成本是否低于增量演进？
3. **长期收益**：切换后能否解决 Ink 的结构性限制？

## OpenTUI 概述

OpenTUI 是一个新兴的终端 UI 框架，相比 Ink 的 React reconciler 方案，它在设计理念上有三个显著差异：

| 维度 | Ink (React Reconciler) | OpenTUI |
|---|---|---|
| 渲染模型 | React 虚拟 DOM + 终端输出 diff | 原生终端渲染管线，直接操作 ANSI 缓冲区 |
| 组件模型 | JSX 组件（React 生命周期） | 声明式布局描述 + 命令式绘制回调 |
| 状态管理 | React useState / useReducer | 自研响应式 Store，不依赖 React 运行时 |
| 事件处理 | Ink useInput() 封装 | 原生 stdin 事件流 + 手势抽象 |
| 依赖体积 | React + Ink + Yoga 布局引擎 | 独立运行时，无框架依赖 |
| 社区成熟度 | 成熟（Ink 5.x，8k+ stars） | 早期（API 可能变动） |

**核心优势**：去掉 React 中间层后，理论上可获得更低的输入延迟、更少的重渲染开销、更小的依赖体积和更直接的终端控制。

**核心风险**：功能等价需要大量自研填补（虚拟滚动、Diff 渲染、主题系统等），且社区生态薄弱。

## 能力对标分析

### 已有能力覆盖度

| 能力 | Ink 现状 | OpenTUI 实现难度 | 风险 |
|---|---|---|---|
| 消息列表 + 虚拟滚动 | Line Estimation + 视口裁剪（约 200 行） | 高——需自研视口裁剪和行高预估 | 中 |
| InputBar 行编辑 | Composer 状态机（纯函数，390 行） | 中层可复用，上层需重写绑定 | 低 |
| 语法级 Diff 渲染 | word-level 高亮（约 250 行） | 高——需自研文本着色和布局 | 高 |
| StatusBar 呼吸动画 | 8 帧橙色脉冲 + 计时器 | 中——需自研帧循环和定时器 | 低 |
| Overlay 弹出层 | 全屏覆盖 + ESC 关闭 | 中——需自研层叠和焦点管理 | 中 |
| Slash 命令系统 | 17 个命令，统一路由 | 中层可复用，路由需重写绑定 | 低 |
| 主题系统 | 命名令牌 + ColorMap | 中——需重新定义色值映射 | 低 |
| CJK/IME 兼容 | Ink 内部处理 | 不确定——OpenTUI 对宽字符兼容性未经验证 | 高 |
| ANSI 转义解析 | 自研解析器（约 150 行） | 低——独立模块可直接移植 | 低 |
| 流式渲染缓冲 | setTimeout 56ms 合并增量 | 中——需自研 ReplayBuffer | 中 |

### 缺失能力（需从零构建）

以下能力在当前 Ink 实现中已有成熟方案，OpenTUI 需要全新实现：

1. **虚拟滚动**：Ink 版的 Line Estimation + 视口裁剪是自研方案，换到 OpenTUI 后需要完全重写。预估工作量 3-5 人天。
2. **Diff 渲染**：word-level 差异高亮依赖 `diff` 库 + 自研着色逻辑。渲染层替换后 Diff 算法可复用，但布局和着色需要重写。预估工作量 2-3 人天。
3. **组件库**：OpenTUI 没有等价于 Ink `Box`/`Text`/`Newline` 的组件体系，需要建立一套基础组件抽象。预估工作量 3-5 人天。
4. **Overlay 管理系统**：全屏弹出层 + z-index + 焦点抢占，当前用 React Context + useState 实现，重写后需要自研状态机。预估工作量 1-2 人天。
5. **主题与样式系统**：CSS-like 的样式继承和组合在当前由 Ink + Yoga 提供，OpenTUI 需要自建。预估工作量 2-3 人天。

## 可复用资产

并非全盘重写。以下模块与渲染层无关，可以直接复用：

- **Composer 状态机**（`composerState.ts`）：纯函数，输入键码输出新状态 + Effect，零依赖
- **ANSI 输入解析器**（`inputKeys.ts`）：自研模块，直接用于 OpenTUI 的 stdin 事件流
- **UiEvent 协议**（`events.ts`）：事件定义和 `projectUiEvent` 投影函数，渲染无关
- **命令实现**（`commands/*.ts`）：17 个 Slash 命令的纯逻辑，仅需替换 UI 绑定
- **会话/上下文管理**（`ReplContext`）：存储、路由、Provider 切换逻辑完全保留
- **Diff 算法**（`diff` 库集成）：word-level 差异计算逻辑不变，仅替换渲染输出
- **渲染器**（`renderers/*.ts`）：ANSI 颜色解析、语法高亮等逻辑复用，替换 JSX 输出

粗略估算，约 40-50% 的代码（按行数）可以直接或少量适配后复用。

### 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| OpenTUI API 不稳定，breaking change 频繁 | 高 | 高——被迫跟进修复 | PoC 阶段先锁定版本，评估稳定性后再决定投入 |
| CJK/IME 兼容性问题无解 | 中 | 高——中文用户不可用 | PoC-8 优先执行，设定 go/no-go 红线 |
| 虚拟滚动性能不如 Ink 版 | 中 | 中——大会话体验下降 | PoC-4 用 500+ 消息压力测试对比 |
| 组件库自建工作量被低估 | 高 | 中——延期 | 优先就地取材（只做必要抽象），不追求通用组件库 |
| 社区生态薄弱，遇到问题无参考 | 高 | 中——排障时间增加 | 做好自行维护的心理准备，必要时 fork |
| 迁移期间 Ink 版仍需维护 | 中 | 低——双线负担 | 用 feature flag 做灰度，Ink 版保留到 GA 后 3 个月 |

## PoC 执行计划

### PoC-0：技术预研（1-2 天）

在进入正式 PoC 之前，先完成以下调查：

- [ ] 阅读 OpenTUI 文档和 API，完整理解其渲染模型和组件体系
- [ ] 在 Vera 项目中跑通 OpenTUI "Hello World"，验证 stdin/stdout 链路和 resize 事件
- [ ] 验证 CJK 字符（中/日/韩）在 OpenTUI 中的渲染宽度是否正确（宽字符 = 2 列）
- [ ] 验证 IME 输入在 OpenTUI 中的行为（组合中文字符是否被切割）
- [ ] 输出一份可行性 memo，明确回答"是否能覆盖现有功能"和"哪些能力需要取舍"

**Go/No-Go 条件**：CJK 渲染和 IME 输入必须通过基本验证，否则不进入后续阶段。

### PoC-1：InputBar 先行（2-3 天）

选择 InputBar 作为第一个移植目标，理由：

- 它是用户感知最强的组件（每个交互都经过它）
- 底层 Composer 状态机和 ANSI 解析器可以直接复用，仅替换渲染层
- 可以快速验证 OpenTUI 的输入事件模型和状态驱动的渲染模式

成功标准：输入行行为与 Ink 版完全一致（光标、补全、历史导航、外部编辑器）。

### PoC-2：消息列表 + 虚拟滚动（5-8 天）

这是整个迁移中最核心也最困难的部分：

1. 先做无虚拟滚动的基础消息渲染（2-3 天），验证消息类型映射
2. 移植 Line Estimation 逻辑（1-2 天），验证行高预估准确性
3. 实现视口裁剪（2-3 天），验证 500+ 消息场景下的滚动性能和正确性

成功标准：100 条消息的场景下，滚动帧率 ≥ 30fps，无视觉闪烁。

### PoC-3：完整功能对等（10-15 天）

依次移植：Slash 命令 UI → Overlay 系统 → DiffView → StatusBar + 动画

成功标准：通过完整的功能冒烟测试 checklist（覆盖所有 17 个命令、5 种 Overlay、Plan Mode）。

## 决策矩阵

| 维度 | 保持 Ink（增量演进） | 切换到 OpenTUI |
|---|---|---|
| **功能完整度** | 100%，已验证 | 未知，PoC 后确定 |
| **开发投入** | 低（每个 Phase 2-5 天） | 高（30-54 天） |
| **性能提升** | 中等（React 优化有限） | 期望高（去掉 reconciler） |
| **维护负担** | React + Ink 大版本升级风险 | 自研组件长期维护成本 |
| **团队技能匹配** | React 生态，人员易招 | 小众框架，学习成本高 |
| **社区支持** | Ink 5.x 活跃维护 | 社区资源少，需自行探索 |
| **长期演化能力** | 受限于 React 终端渲染的限制 | 完全控制渲染管线，定制性强 |
| **回退成本** | 无（每次增量可回退） | 高（全量迁移后几乎不可回退） |

### 建议

**短期（0-3 个月）**：继续执行 [Ink 增量演进方案](./tui-ink.md)，完成 Phase 1-5 的 App 拆分、Composer 模块化、事件协议严肃化、视口抽象和性能优化。这些改进无论最终是否切换框架，都能提升代码质量和可维护性。

**中期（3-6 个月）**：如果 Ink 演进方案完成了 Phase 1-4 后仍存在以下问题，启动 OpenTUI PoC-0 和 PoC-1：

- Ink 的 React reconciler 成为性能瓶颈（消息数 > 500 时明显卡顿）
- Ink 大版本升级导致 breaking change 无法消除
- 团队有富余人力可以做技术预研（至少 0.5 人）

**触发切换的条件**（需同时满足）：

1. PoC 全部通过，功能等价覆盖率 ≥ 95%
2. OpenTUI API 稳定至少 2 个 minor 版本（或团队愿意 fork 维护）
3. 性能基准测试表明 OpenTUI 版在 500+ 消息场景下显著优于 Ink 版（延迟降低 ≥ 30%）
4. CJK/IME 兼容性达到 Ink 同等水平

**不切换的场景**：

- 增量演进解决了核心痛点，性能可接受
- OpenTUI 社区不活跃，API 频繁变动
- CJK/IME 兼容性无法达到可用标准
- 团队资源紧张，无暇承担 30+ 天迁移

## 结论

OpenTUI 重写是一个高投入、高风险的选项。它在理论上能解决 Ink 的架构限制（React overhead、Ref 瀑布、虚拟 DOM diff），但实际收益需要 PoC 验证。当前阶段的理性策略是：**先完成 Ink 增量演进，同时以极低成本做 OpenTUI 技术预研（PoC-0），拿到一手数据后再做最终决策。** 在此之前，不做任何重写的承诺或架构假设。
