# OpenVera — 路线图

## 指导原则

本路线图不是一个功能清单——它是 OpenVera 的分阶段运营策略。目标不是追赶现有的 agent 产品，而是构建一个**能自规划、自循环、自批判、自进化的 Harness 原生 agent 运行时**。

> Vera 不只是执行任务。在 Harness 的约束下，它规划自己的流程、驱动自己的循环、批判自己的结果、积累经验并驱动系统进化。

### 核心判断

Harness 不被视为"安全外壳"——它是**系统内核**。

- Agent 不直接接触工具——Harness 调度工具调用。
- Agent 不直接决定是否继续——Harness 管理流转状态。
- Agent 不直接修改自身——Harness 管理批判、提案、发布上线与验证。

没有这个内核设计，自规划、自循环和自进化就变成了不可靠的提示词技巧，而非工程化的系统能力。

### 已知缺陷与技术债

> P0 实现已完成，但 2026-04-28 架构审计发现了必须在 P1 开始前修复的运行时缺陷和薄弱点。**所有严重、高、中等级别的问题均已解决。**

**严重（全部已修复）：**
- C1：微精简时间戳 bug（无限上下文实际上不工作）
- C2：loop.ts 中对工具参数使用裸 `JSON.parse`（畸形 JSON 导致 agent 循环崩溃）
- C3：工具结果为空后仅重试 1 次
- C4：流式传输缺少错误恢复
- C5：Harness 步骤依赖缺少循环检测

**高（全部已修复）：**
- H1：测试覆盖率约 8.5%，核心路径未验证
- H2：压缩状态变更为非原子性
- H3：Gemini 流式传输无用量报告
- H4：批判无内部重试循环
- H5：审批流程（`waiting_approval`）不完整
- H6：无步骤级超时或预算约束

**中（全部已修复）：**
- M1-M6：Token 估算、窗口裁剪、工具结果计时、压缩成本追踪、planId 冲突风险

```
[已完成] 意图路由
[已完成] 会话持久化 + 费用追踪
[已完成] 工具运行时基础
[已完成] 工具输出渲染
[已完成] 计划模式基础
[已完成] AgentHooks 分层钩子系统
[已完成] 自循环运行时（P1）
[已完成] 检查点/恢复
[已完成] 记忆系统
[已完成] 子 Agent 系统
[已完成] P2：基准测试 Harness -> Dreaming -> 提案管道
[已完成] P3：计算机使用 / MCP / 多 Agent / 自适应策略
```

执行原则：
1. 先构建 harness 内核，再构建 agent 智能。没有内核，自循环和自进化只会导致混乱。
2. 先构建运行时，再构建更复杂的策略层。没有稳定的执行层，记忆和 dreaming 只是空中楼阁。
3. 先构建批判和基准测试，再进行大规模优化。没有批判和评估，进化就不可证伪。

## 架构说明

### Core / Harness 边界

**Core** = 单次 LLM 调用的最小循环：adapter -> stream -> 工具调用 schema -> ToolResult。
**Harness** = 多步工作流：ExecutionPlan 状态机、流转状态、批判循环、检查点。

依赖：`harness -> core`。Core 不感知 Harness。

| 关注点 | 归属 |
|---------|-------|
| LLM 适配器 / 流式传输 | Core |
| 工具 schema + ToolResult 类型 | Core |
| ToolLifecycleHook 接口 | Core |
| ToolRegistry + 内置工具实现 | Core |
| HarnessPlugin（路径/预算/注入） | Core（注册为钩子，由 Harness 配置） |
| ExecutionPlan / Step / 流转状态 | Harness |
| 批判 / 提案 / 发布 | Harness |
| 检查点 / 恢复（计划层面） | Harness |
| 会话 JSONL 持久化 | Core（由 Harness 读写） |

### 两种"计划"

- **Agent 计划**（LLM 文本输出）：模型在 assistant 消息中以自然语言输出的计划，非结构化，供人阅读。
- **Harness ExecutionPlan**（运行时数据结构）：一个状态机，包含 `Step[]`、`currentStepIndex`、`status`，控制实际执行流程。

这是同一事物的两个阶段：LLM 输出文本计划 -> Harness 解析为 ExecutionPlan -> 逐步驱动工具调用。

### AgentRunner 接口

Harness 在分发计划步骤时需要调用 agent（LLM 执行步骤）。为避免 Harness 直接从 Core 导入 `runAgent`（紧耦合），接口在 Core 中定义：

```ts
// packages/core/src/types/agent.ts
interface AgentRunner {
  run(prompt: string, tools: Tool[], ctx: RunContext): Promise<AgentResult>;
}
```

Harness 依赖 `AgentRunner` 接口。Core 提供默认实现。未来的 agent 引擎（LangGraph、AutoGen）可替换而无需修改 Harness。

## 基准测试计划

基准测试不是为了"分数"——而是回答具体问题：agent 在哪些任务类型上可靠完成、在哪里失败、以及为什么。

### 评估维度

| 维度 | 衡量内容 | 方法 |
|-----------|-----------------|--------|
| 任务完成率 | 能否达成目标 | 通过/失败，N 次重复取平均 |
| 工具调用准确率 | 工具选择是否正确、参数是否准确 | 与标准工具调用对比 |
| 步骤效率 | 完成需要的步骤数 | 统计轮次 |
| Token 效率 | 每个任务消耗的 token | 从 usage 字段获取 |
| 稳定性 | 5 次运行的一致性 | 方差/标准差 |

### 开源基准测试

**通用 Agent 能力：**
- **GAIA**（HuggingFace）：多步推理 + 工具使用，L1/L2/L3 分层，社区排行榜——建议从 L1 开始
- **AgentBench**：8 个真实环境（OS、DB、Web、游戏等）
- **SWE-bench Verified**：真实 GitHub issues 供 agent 修复——代码场景专长

**工具调用：**
- **ToolBench / ToolEval**：16,000+ 真实 API，测试工具选择和参数生成
- **API-Bank**：分层难度，单次调用 vs 多步

**推理与规划：**
- **ALFWorld**：文字游戏环境，测试规划链
- **HotpotQA / MuSiQue**：多跳问答，适合检索增强型 agent

**计算机使用专项：**
- **WebArena**：在真实网站上的多步 Web 任务
- **OSWorld**：跨应用桌面操作，截图 + 动作序列
- **ScreenSpot**：GUI 定位，点击正确元素

### 推荐策略

1. 首先运行 **GAIA L1**：体量适中，标准答案，有社区可对比
2. 代码场景成熟后运行 **SWE-bench Verified**（子集）
3. 计算机使用上线后运行 **WebArena**
4. **构建自定义用例**，覆盖开源套件遗漏的场景

### 何时运行基准测试

- 修改提示词或循环逻辑后
- 比较模型时（Claude vs GPT vs Gemini）
- CI 中作为回归测试（仅 L1，快速且便宜）
